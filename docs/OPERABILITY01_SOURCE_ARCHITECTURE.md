# OPERABILITY01 — Source Architecture Amendment — frozen before first fresh classification

Date: 2026-08-14.

This document clarifies data-source architecture only. It does not change any OPERABILITY01 threshold, metric, deterministic gate, fresh-forward boundary, or governance rule.

## Why this amendment exists

The first execution of OPERABILITY01 used the large Market Chronos research M5 parquet for both threshold reference and prospective rows. That execution returned `WAITING_FOR_FRESH_FORWARD_DATA`: no row at or after `2026-08-13 00:00:00 BRT` existed in that parquet. Therefore no fresh-forward state was classified and no prospective outcome or operability result was observed before this source split.

The production `Base_Dados.py` intentionally maintains a smaller live intraday window, while the research candle base contains the large historical sample. Those are different responsibilities and should not be forced into one file.

## Frozen two-source architecture

### REFERENCE_M5 — large research sample

Source: `data/market_chronos/candle_base/timeframes/` resolved to the GOLD M5 research parquet.

Purpose only:
- reproduce the frozen TRAIN reference strictly before `2026-01-09 12:50:00 BRT`;
- reproduce the q0.990/q0.995 thresholds for `RANGE_ATR`, `ABS_RET_ATR`, and `GAP_ATR`;
- enforce expected TRAIN metric count `n=22631` before any prospective classification.

Rows after TRAIN_END in the reference file are irrelevant to threshold estimation and are never used to optimize the gate.

### LIVE_M5 — small rolling live sensor

Source: `data/GOLD_M5.parquet`, generated by the existing `Base_Dados.py --mode intraday_refresh --symbol GOLD` flow.

Purpose only:
- provide closed causal M5 bars for prospective classification at or after `2026-08-13 00:00:00 BRT`;
- apply the already-frozen thresholds and deterministic operability rules;
- never refit or recalibrate anything.

The LIVE file does not need the full historical research sample. It only needs sufficient recent history for the already-existing M5 features/ATR and previous-close calculations.

## Persistent shadow ledger

Because LIVE_M5 is a rolling window, OPERABILITY01 must not depend on it to preserve the whole fresh-forward history.

`data/market_chronos/operability/GOLD_operability_shadow.csv` is therefore append-only by `available_at_brt`:
- a new unseen closed M5 timestamp is classified once and appended;
- a timestamp already present in the shadow ledger is not reclassified by later runs;
- `SHADOW_FIRST_CLASSIFIED_AT_UTC` records when the row first entered the prospective ledger;
- the short live parquet may roll forward without deleting earlier shadow evidence.

This prevents later code/data changes or newly added event metadata from silently rewriting already-observed shadow classifications.

## Operational runner

`OPERABILITY01_live_cycle.py` runs, in order:

1. `Base_Dados.py --mode intraday_refresh --symbol GOLD`
2. `OPERABILITY01_shadow_gate.py`

If the MT5 refresh fails, the shadow classifier is not executed.

## Governance preserved

- Historical timing rescue remains prohibited.
- `HISTORICAL_TIMING_FEATURE_DISCOVERY_STOP=YES` remains active.
- Exp27 remains untouched and unscored.
- Runtime promotion remains NONE / SHADOW ONLY.
- No future outcome, PnL, EXIT label, trade result, or fresh-forward performance is read by OPERABILITY01.
